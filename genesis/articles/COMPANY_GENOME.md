**Project:** Studio OS  
**System:** Company Genome™  
**Status:** Constitutional architecture proposal for Genesis review  
**Version:** 3.0.0  
**Authority:** Genesis.md  
**Supersedes:** Company Genome™ v2 documentation model as the constitutional

**Depends on:** Founder context, Business Discovery™, Canonical Object Model™,

---

## 0. Constitutional decision

**Approve the direction with a critical boundary.**

Company Genome™ should become the **canonical living organizational model** for
every company inside Studio OS.

It must become the single source of truth for:

- what the company is
- how it creates and captures value
- which capabilities and organizational structures it requires
- which constraints, authorities, policies, and commitments govern it
- how its canonical organizational objects relate
- what the system has learned about the company, with evidence and confidence

It must **not** become the single database for every fact, transaction, runtime
state, workflow execution, conversation, asset, or analytic event.

```text
Company Genome™ is the source of organizational meaning.
It is not the source of every operational record.
```

This distinction prevents a “universal repository” from becoming a slow,
duplicated, unsafe system of record.

## 1. Prime directive

```text
Every company in Studio OS has one living organizational genome.
Every major system consults it before it interprets, proposes, compiles, or acts.
No system duplicates its canonical organizational meaning.
```

Company Genome™ is not documentation, a profile, a CRM, a dashboard, or a
static onboarding record.

It is the versioned organizational digital twin that connects:

```text
Founder intent
  -> business architecture
  -> operating model
  -> organizational capabilities
  -> governance and constraints
  -> canonical relationships
  -> evidence-based learning
  -> system-specific projections
```

## 2. What “single source of truth” means

The phrase is valid only when scoped precisely.

### 2.1 Company Genome™ is authoritative for

| Truth class | Examples |
|---|---|
| **Organizational identity** | mission, purpose, values, company stage, strategic posture |
| **Business architecture** | business model, revenue model, offer model, economics, customer lifecycle, value streams |
| **Operating model** | capabilities, department topology, accountabilities, service levels, capacity assumptions, control points |
| **Governed organizational constraints** | authority boundaries, policy references, compliance obligations, data classification, risk posture |
| **Canonical organizational relationships** | company → department → capability → workflow → system → owner relationships |
| **Organizational learning** | verified beliefs, preferences, patterns, constraints, decisions, outcomes, confidence, provenance |
| **Projection contracts** | which downstream systems may derive or consume which versioned organizational brief |

### 2.2 Company Genome™ is not authoritative for

| Truth class | Authoritative owner |
|---|---|
| Invoice, order, inventory, shipment, payroll, CRM interaction | The relevant transactional system of record |
| Workflow execution state, retries, timers, event delivery | Workflow Engine™ / event infrastructure |
| Mission progress, assignments, blockers | Mission Control™ |
| A founder conversation, command, or temporary intent interpretation | Orb™ / Command Center™ |
| Evidence corpus and searchable knowledge content | Institute of Knowledge™ / Knowledge Core™ |
| Brand strategy and creative judgment | Strategic Brand DNA™ / Brand Discovery Engine™ |
| Experience-expression definitions | Experience Engine™ |
| Resolved UI state and rendering lifecycle | Experience Runtime™ |
| A recommendation, confidence calculation, or reasoning trace | Studio Intelligence Layer™ / Decision architecture |
| Asset binary, media rendition, delivery state | Asset Registry / storage systems |

Each of those systems must reference the relevant Genome version when
interpreting organizational context.

## 3. Correct constitutional model

The following proposition is rejected:

```text
Company Genome owns everything.
Everything else is merely a passive derived copy.
```

It would erase responsibility boundaries and make execution systems unable to
maintain their own auditable state.

The approved proposition is:

```text
Company Genome™ owns canonical organizational meaning.
Specialized systems own their native state and behavior.
Every material projection declares its Genome version and source relationships.
```

### 3.1 Organizational dependency graph

```text
Founder Genome™ / Founder Decision Context
  -> Business Discovery™
    -> Company Genome™
       ├─ Organizational Identity
       ├─ Business Architecture
       ├─ Operating Model
       ├─ Governance & Constraint Model
       ├─ Organization Graph
       └─ Organizational Learning Ledger
            |
            +-> Company Operating Manual™      [doctrine]
            +-> Department Operating Charters™ [department contracts]
            +-> Workflow Engine™               [execution graphs]
            +-> AI Workforce Model™            [role + authority envelopes]
            +-> Strategic Brand DNA™           [business constraints]
            +-> Studio Intelligence Layer™     [reasoning context]
            +-> Narrative / Creative / Production systems
            +-> Executive Headquarters™        [capability and briefing model]
            +-> Experience Compiler™           [contextual selection]
                  -> Experience Engine™
                    -> Experience Runtime™
```

Composition is the default. Inheritance is only used within a same-kind family,
such as Experience Brand DNA™ → Experience Department DNA™.

## 4. Genome domains

### 4.1 Organizational Identity

Owns the stable answer to:

```text
Who is this company, why does it exist, and what must it not become?
```

Required fields:

- company identity, legal/operating entity references, jurisdiction
- mission, purpose, values, long-term ambition
- founder and executive philosophy references
- company stage, strategic horizon, growth posture
- success definition and strategic metrics
- non-negotiables and anti-patterns

### 4.2 Business Architecture

Owns the answer to:

```text
How does this company create, deliver, capture, and sustain value?
```

Required fields:

- industry/category and market context
- business, revenue, pricing, margin, and cost-to-serve model
- product, service, offer, membership, and marketplace architecture
- customer segments, buying roles, jobs, lifecycle, and trust requirements
- fulfillment, logistics, manufacturing, procurement, inventory, or delivery
  model when applicable
- channel, partnership, licensing, intellectual-property, and data-value model
- unit economics, capital constraints, key dependencies, resilience posture
- regulatory, privacy, rights, and compliance constraints

### 4.3 Operating Model

Owns the answer to:

```text
What enduring capabilities, accountabilities, and coordination patterns are
required to deliver this company’s promise?
```

Required fields:

- value streams and operating lifecycle
- capability map and required departments
- organization topology, ownership, decision rights, and escalation paths
- department interfaces, handoff contracts, and service levels
- capacity, resource, vendor, and partner assumptions
- control points, risk classes, audit requirements, and continuity posture
- systems-of-record map and integration boundaries
- automation eligibility and human-in-the-loop boundaries
- measurement model, feedback loops, and change-management rules

### 4.4 Governance & Constraint Model

Company Genome™ stores the canonical **relationships and applicability** of
governance—not a second copy of every policy document.

It owns:

- applicable policy references and versions
- compliance obligations and controls
- data classification and residency constraints
- authority boundaries and founder approval triggers
- risk appetite and prohibited action classes
- required review and evidence thresholds
- exception, incident, and continuity requirements

The Company Operating Manual™ remains the source of operational doctrine.
The Policy Engine™ remains the source of executable policy evaluation.

### 4.5 Organization Graph

The Organization Graph makes organizational structure queryable:

```text
Company
  -> Value Stream
    -> Capability
      -> Department
        -> Department Operating Charter
          -> Role / AI Workforce Role
          -> Workflow
          -> System of Record
          -> Metric
          -> Risk / Control
```

This graph is canonical organizational topology. It does not duplicate a
workflow’s execution graph or a system’s transaction records.

### 4.6 Organizational Learning Ledger

The Genome retains versioned, confidence-scored organizational beliefs:

- founder decisions and overrides
- validated business assumptions
- operating preferences and observed constraints
- approved/rejected organizational patterns
- performance-derived lessons
- strategic/creative/brand/operational discoveries
- contradiction records and unresolved questions

Every entry must have:

- provenance
- evidence references
- confidence
- owner
- scope
- effective date
- review/expiry rule
- relationship to the affected Genome domain

## 5. Derived systems and ownership boundaries

### 5.1 Company Operating Manual™

The Manual is a **governed doctrine projection** of Company Genome™ plus
approved procedures and policies.

```text
Genome: what organizational model applies
Manual: how people and AI workers must operate within it
```

The Manual may add detailed procedures. It cannot silently alter the Genome’s
business architecture, authority model, or organizational constraints.

### 5.2 Department Operating Charters™

Each charter derives its mandate, interfaces, authority, and capacity assumptions
from the Operating Model™.

It owns department-specific operational detail and change history.

It must not be confused with **Experience Department DNA™**, which is a visual
and interaction-expression layer inheriting from Experience Brand DNA™.

### 5.3 AI Workforce Model™

AI workforce roles are not “created from a department list.”

They are derived as governed role envelopes:

```text
Operating capability
  -> accountable role
  -> allowed work classes
  -> accessible data classes
  -> approval limits
  -> escalation policy
  -> required manual/workflow references
```

Company Genome™ owns the organizational need and authority envelope. The AI
Workforce system owns provisioning, execution state, performance, and worker
memory.

### 5.4 Strategic Brand DNA™

Brand DNA™ is not a mutable child of Business Architecture.

It receives a versioned **Business Architecture Brief™** with commercial,
audience, category, trust, and regulatory constraints. It remains the
authoritative owner of strategic identity, positioning, voice, distinction, and
creative expression.

Conflicts between brand ambition and business constraint are Decision DNA™
objects requiring governed resolution.

### 5.5 Workflow Engine™

Operating Model™ provides workflow candidates, ownership, lifecycle boundaries,
controls, and service-level expectations.

Workflow Engine™ owns executable graph definition, event handling, state,
retries, compensation, observability, and audit.

```text
Genome constrains and contextualizes a workflow.
Workflow Engine executes it.
```

### 5.6 Studio Intelligence Layer™

Studio Intelligence™ must consult a pinned Company Genome snapshot to reason
about company context.

It owns:

- evidence retrieval and context assembly
- recommendations, alternatives, confidence, and trade-offs
- Decision DNA™ reasoning and founder preference interpretation
- intelligence-specific learning proposals

It does not own a second organizational model.

### 5.7 Experience Engine™, Runtime™, and Studio Experience™

Experience systems consume a compiled organizational context:

- permitted roles and role hierarchy
- department/capability semantics
- approved experience requirements
- policy-safe state/interaction constraints
- Business/Operating/Brand brief version IDs

They do not derive visual identity directly from raw economic data or operating
doctrine.

```text
Company Genome + intelligence + Brand DNA
  -> Experience Compiler™
    -> Experience DNA™
      -> Experience Engine™
        -> Experience Runtime™
          -> Studio Experience™
```

### 5.8 Institute of Knowledge™, Orb™, and Mission Engine™

| System | Relationship to Company Genome™ |
|---|---|
| **Institute of Knowledge™** | Stores source evidence, approved doctrine, learning records, and educational artifacts; Genome references and summarizes their organizational implications. |
| **Orb™** | Composes answers/recommendations from a pinned Genome snapshot plus evidence; owns no Genome truth. |
| **Mission Engine™** | Uses strategic priorities, value streams, constraints, and capability ownership to formulate missions; owns mission lifecycle and outcomes. |

## 6. Learning, versioning, and contradiction

### 6.1 Learning law

```text
Signal
  -> evidence assessment
  -> Genome learning proposal
  -> confidence / impact evaluation
  -> required review
  -> approved Genome revision
  -> downstream projection invalidation
  -> selective recompilation
```

Signals include founder decisions, production outcomes, customer feedback,
workflow outcomes, finance/operations data, policy changes, and approved
knowledge.

No raw signal may directly rewrite a canonical organization model.

### 6.2 Versioning law

Every material consumer must declare:

- `companyGenomeId`
- `companyGenomeVersion`
- `snapshotHash`
- source references
- compatibility / staleness policy

Every generated workflow, department charter, AI workforce envelope, experience
brief, and headquarters proposal must be reproducible from its pinned inputs.

### 6.3 Contradiction law

The Genome must represent disagreement, not average it away.

Examples:

- Founder says premium service; revenue data favors discounting.
- Brand promise says white-glove support; capacity model cannot sustain it.
- AI workforce request requires data access prohibited by policy.

Each contradiction becomes a governed object with evidence, impact, owner,
options, and decision requirement.

## 7. New-company onboarding

Twenty strategic questions can create a useful **provisional** organizational
model. They cannot create a complete or permanent company truth.

### 7.1 Discovery sequence

```text
Founder context
  -> Company purpose and non-negotiables
  -> Value creation and customer promise
  -> Offers, economics, lifecycle, fulfillment
  -> Operating capabilities and current bottlenecks
  -> Authority, risk, compliance, and data constraints
  -> Brand aspiration and experience requirements
  -> Contradictions and confidence gaps
  -> Provisional Company Genome™
  -> Founder validation
```

### 7.2 Projections from a validated Genome

```text
Validated Company Genome™
  -> Company Operating Manual™ draft
  -> Department Operating Charter™ proposals
  -> AI Workforce authority-envelope proposals
  -> Workflow Engine™ graph proposals
  -> Strategic Brand DNA™ brief
  -> Executive Headquarters™ capability proposal
  -> Experience DNA™ proposal
  -> Adaptive workspaces
```

### 7.3 Activation gates

| Gate | Required before |
|---|---|
| Founder validates core organizational model | Any external or high-impact action |
| Authority, data, and approval model approved | AI worker execution |
| Manual and workflow pass validation | Automation activation |
| Brand and experience approval | Public touchpoint deployment |
| Runtime QA / accessibility / policy validation | Workspace activation |

## 8. Scalability and safety

### 8.1 Multi-tenant rule

- Every Genome, snapshot, learning entry, and projection is tenant-scoped.
- Cross-company learning requires explicit consent, anonymization, provenance,
  and policy approval.
- Company templates are reusable schemas, never shared mutable company truth.

### 8.2 Data and performance rule

Company Genome™ stores semantic references and tested snapshots, not copies of
high-volume operational records.

It must use event references, aggregation contracts, and projection caches
rather than becoming a data warehouse or transaction bus.

### 8.3 Authority rule

Company Genome™ can constrain an action and trigger review. It cannot execute
an action merely because it models the organization.

Execution remains governed by permissions, policy, approvals, workflow state,
and human override.

## 9. Anti-patterns

Company Genome™ must never become:

- a documentation folder presented as intelligence
- a CRM, ERP, WMS, accounting ledger, or data warehouse
- a duplicate copy of every system’s native state
- an unreviewed inference engine that rewrites company doctrine
- a hidden configuration store behind the Headquarters UI
- a substitute for Brand DNA™, Workflow Engine™, Experience Engine™, or
  Studio Intelligence™
- a universal “inheritance parent” that forces unrelated systems into a linear
  hierarchy

autonomous/high-impact activation gates.

   reviewed together.
