## 0. Architectural challenge

The default assumption is:

```text
A prompt library is a searchable folder of useful prompts.
```

That assumption is too small for Studio OS.

Studio OS is being built through architecture prompts, implementation prompts, validation prompts, design prompts, research prompts, and future AI workflows. If those prompts are treated as files, snippets, chats, or private agent memory, Studio OS loses the reasoning chain that created itself.

The superior architecture is:

```text
Every approved prompt becomes a reusable institutional knowledge asset with identity,
versioning, relationships, execution history, outputs, validation results, lessons,
model performance, and Genesis lineage.
```

The Architect's Prompt Library™ is therefore not a folder.

It is an **Institute of Knowledge™ institution** and the internal operating manual for building Studio OS.

### 0.1 Prime directive

```text
Studio OS must remember how it was prompted into existence, why each prompt worked,
what it produced, and how future prompts should improve.
```

### 0.2 Product promise

Years from now, any founder, engineer, employee, AI model, or future Studio OS company should be able to ask:

> "How was this system designed, what prompt created it, why did that prompt work, and what should we use next?"

## 4. Prompt lifecycle

```text
Draft
  -> Review
  -> Execution
  -> Output Review
  -> Founder Approval
  -> Genesis References Updated
  -> Canonized
  -> Archived
```

### 4.1 Draft

Prompt is created with purpose, category, context requirements, expected deliverables, and dependencies.

Draft quality gate:

- clear purpose
- no ambiguous deliverables
- required context named
- expected artifacts named
- model recommendation justified

### 4.2 Review

Orb and/or human reviewer checks:

- architectural fit
- duplication
- conflict with Genesis
- prompt clarity
- model suitability
- safety
- output measurability

### 4.3 Execution

Execution captures:

- model
- context
- artifacts
- runtime
- operator
- output summary

### 4.4 Output Review

The output is reviewed against expected deliverables.

Review classes:

- complete
- incomplete
- architecturally strong but implementation weak
- implementation strong but concept weak
- needs founder context
- needs Genesis review
- should not be reused

### 4.5 Founder Approval

Required for canonical prompt templates that shape:

- Genesis
- Launch Stack
- founder experience
- Executive Headquarters
- brand doctrine
- company operating model
- platform expansion

### 4.6 Genesis References Updated

If a prompt produces canonical architecture, it must link to Genesis articles, proposals, ADRs, or review sessions.

### 4.7 Canonized

Canonized prompts become recommended operating instructions.

They are searchable, reusable, and model-aware.

### 4.8 Archived

Archived prompts remain discoverable for history but are not recommended for new use.

## 5. Prompt quality system

Every prompt receives quality scores.

### 5.1 Quality dimensions

| Dimension | Measures |
|-----------|----------|
| **Architectural Quality** | System fit, dependency awareness, Genesis alignment |
| **Implementation Quality** | Produces buildable, maintainable changes |
| **Output Consistency** | Repeated runs produce reliable structure |
| **Reusability** | Works across companies/systems without brittle context |
| **Platform Value** | Improves Studio OS itself |
| **Business Value** | Helps companies operate better |
| **Founder Value** | Improves founder clarity, confidence, or decision quality |
| **Knowledge Value** | Produces reusable institutional learning |
| **Validation Readiness** | Output can be tested/reviewed objectively |
| **Model Portability** | Performs acceptably across alternative models |

### 5.2 Score interpretation

| Score | Meaning |
|-------|---------|
| 90-100 | Canonical-grade |
| 80-89 | Strong reusable prompt |
| 70-79 | Useful but needs refinement |
| 60-69 | Context-sensitive / not broadly reusable |
| Below 60 | Do not canonize |

Quality scores should be recalculated after executions and reviews.

Models may include:

- GPT-5.5
- Composer
- Future Models
- Studio Foundation Models™
- Profession Models™
- local/offline models

### 6.1 Model comparison dimensions

- speed
- consistency
- architecture
- implementation
- reasoning
- creative direction
- technical accuracy
- long-form output
- prompt success rate
- instruction adherence
- codebase awareness
- revision quality
- cost if available

### 6.2 Model recommendations

The Library should recommend:

- best model
- acceptable alternatives
- avoid models
- context window requirement
- reasoning level
- expected runtime
- quality confidence

Recommendation example:

```text
For canonical architecture prompts: use GPT-5.5 high reasoning unless the prompt
requires broad codebase edits, then use Composer/Codex-style implementation flow.
```

The recommendation must be evidence-backed from execution history, not brand preference.

## 7. Prompt evolution intelligence

The Library should continuously identify:

- duplicate prompts
- outdated prompts
- conflicting prompts
- missing prompts
- merge opportunities
- prompt improvement opportunities
- automatic optimization candidates
- prompts without validation
- prompts with poor model fit
- prompts with high value but low discoverability

### 7.1 Duplicate detection

Signals:

- overlapping purpose
- same expected artifacts
- same Genesis references
- same category + similar body
- repeated execution producing same result

### 7.2 Conflict detection

Signals:

- contradictory Genesis references
- conflicting implementation approaches
- different model recommendations without rationale
- prompts that produce incompatible artifacts
- obsolete architecture assumptions

### 7.3 Missing prompt detection

Coverage gaps:

- Genesis article has no implementation prompt
- system has no validation prompt
- room has no design prompt
- engine has no test prompt
- Launch Stack milestone lacks founder acceptance prompt
- recurring manual workflow lacks automation prompt

## 10. Governance

### 10.1 Canonical prompt requirements

A prompt may become canonical only when:

1. Purpose is clear.
2. Required context is explicit.
3. Expected deliverables are measurable.
4. Dependencies are declared.
5. At least one execution is reviewed.
6. Output quality passes threshold.
7. Genesis references are accurate.
8. Known limitations are documented.
9. Review/approval status is complete.
10. It has an owner/steward.

### 10.2 Prompt review roles

| Role | Responsibility |
|------|----------------|
| **Author** | Drafts prompt |
| **Orb Curator** | Recommends, reviews, detects gaps/conflicts |
| **System Steward** | Confirms system accuracy |
| **Founder** | Approves prompts shaping permanent founder/company/Genesis experience |
| **Genesis Reviewer** | Confirms canonical references and governance |
| **Implementation Reviewer** | Confirms code/artifact quality |

### 10.3 Approval boundaries

Founder approval required for:

- Genesis-changing prompts
- Executive Headquarters prompts
- Orb behavior prompts
- founder experience prompts
- company identity prompts
- brand doctrine prompts
- irreversible architecture prompts
